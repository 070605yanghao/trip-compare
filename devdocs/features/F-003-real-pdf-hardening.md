# F-003 — 真实说明书加固与 Demo 同步

## 概述

用四份真实旅行社 PDF 验收并加固解析器；把线上 Demo（docs/ → GitHub Pages）从旧版报告更新为新版。

## 用户故事

作为选品人，我上传真实供应商的说明书（包括图片型扫描件），报告不该出现正文碎片当产品名、「单人房费」当人群定位这类一眼假的错误。

## 验收标准

- [x] 标题提取必须有天数、排除说明类行；取不到回退文件名
- [x] 正文提不到天数时回退文件名，依据注明「文件名：…」
- [x] 定位人群要求定位语境词，「单人房费」「蜜月拍照喜字」不再污染
- [x] 行程覆盖丢弃括号未闭合的残缺途经点
- [x] 「没有+抒情句」不被当成「明确不包含」
- [x] 包含服务过滤裸段头「费用包含」
- [x] docs/ 四件（两份 HTML + 两份 JSON）用新代码重新生成并推送，Pages built

## UX 流程

报告结构不变；真实四线路报告的矩阵列头显示正确产品名（M1-A 列 = 粉雪冬日7天6晚）。

## 数据模型影响

无字段结构变化；行为变化：标题/天数增加文件名兜底策略（D-005，schema.md 变更记录已记）。

## 输出契约

docs/ 新增 `sample-data.json`、`beijiang-data.json`（结构化数据随报告一并发布）。

## 报告说明

遵循 `report-standards.md`；真实数据下滑雪/旅拍多为「~ 表述模糊」属设计的保守判定（原文确实既写含票又写雪票自理），非 bug。

## 测试计划

- 新增 6 项加固测试（标题回退/标题优先正文/人群语境/天数兜底+依据/残缺括号/抒情句不判不含）
- 全量：56 项（2+12+42）实跑全绿（2026-10-18）
- 渲染核查：Chrome 无头截图两份 Demo 页

## 假设

- 文件名可信（旅行社文件命名普遍含天数与线路名）
- M1-A 图片型说明书文字层极少（4.7KB），住宿配置等字段显示「—」是可接受现状，OCR 兜底见 I-001
